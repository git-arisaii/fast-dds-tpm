# TPM-enabled Fast DDS
This repository contains a fork of the eProsima FastDDS implementation, extended by TPM-based remote attestation.
Try it out using the included Dockerfile.
```
git clone https://gitlab.cc-asp.fraunhofer.de/ros2-security/fast-dds-tpm && cd fast-dds-tpm
docker build -t fast-dds-tpm .
docker run --rm -it fast-dds-tpm
> cd install/examples/cpp/dds/SecureHelloWorldWithTPMExample/bin/
> ./generate_quoting_key.sh /CN=myQuotingKey/OU=myCompany
> ./DDSSecureHelloWorldWithTPMExample publisher &
> ./DDSSecureHelloWorldWithTPMExample subscriber
```

## Prerequisites
This fork of FastDDS extends the DDS PKI-DH authentication and access control plugins with TPM-based remote attestation capabilities.
The only additional prerequisite is the [TPM 2.0 TSS](https://github.com/tpm2-software/tpm2-tss), which can be installed from the package manager with most Linux distributions.
```
apt-get install -y tpm2-tools tpm2-openssl man-db libtss2-dev
```

## Prepare the TPM
To enable remote attestation in DDS, you first need to prepare an attestation key inside the TPM.
You can use the powerful [TPM2 Tools](https://tpm2-tools.readthedocs.io) for this.
```
# Create a new endorsement key with handle 0x81010001.
# You can skip this step if your TPM already has an EK provisioned (like the simulator in the Dockerfile).
tpm2_createek -c 0x81010001 -G rsa -g sha256

# Create a new attestation key under the EK and make it persistent
tpm2_createak -C 0x81010001 -G rsa -g sha256 -c quotingkey.ctx
tpm2_evictcontrol -c quotingkey.ctx -o quotingkey.tr
```

You also need to generate a certificate for the created attestation key that is signed by your CA.
To try out remote attestation in DDS, it is sufficient to just use the TPM provider of OpenSSL for this.
```
openssl req -provider tpm2 -provider default -propquery '?provider=tpm2' -new -subj "/CN=myQuotingKey/OU=myCompany" -key object:quotingkey.tr -out quotingkey.csr
openssl x509 -req -CA maincacert.pem -CAkey maincakey.pem -days 730 -in quotingkey.csr -out quotingcert.pem
```
ATTENTION:
Note that generating a self-signed CSR for the attestation key like that does not allow the CA to verify that the attestation key is in fact protected by a genuine TPM.
Hence, in production scenarios you should instead establish a proper provisioning process for attestation keys and certificates, following the TCG guidelines.
Refer to [TPM 2.0 Keys for Device Identity and Attestation](https://trustedcomputinggroup.org/wp-content/uploads/TCG_IWG_DevID_v1r2_02dec2020.pdf) for further details.

## Configure Remote Attestations
To configure a DDS participant for remote attestation, all you need to do is to set the following QoS properties in the `dds.sec.auth.builtin.PKI-DH.tpm2` namespace.

| Property      | Description                                                          | Example                |
| ------------- | -------------------------------------------------------------------- | ---------------------- |
| quoting_key   | Attestation key to use for generating quotes.                        | handle:0x81000000      |
| quoting_cert  | CA-signed certificate authenticating the attestation key.            | file://quotingcert.pem |
| privacy_ca    | CA certificate to authenticate remote attestation keys. Optional.    | file://maincacert.pem  |
| pcr_banks     | PCR banks to include in the generated quotes.                        | sha1,sha256            |
| pcr_selection | PCR registers to include in the generated quotes.                    | 0-7,10                 |
| tcti_options  | TCTI parameter string, e.g. to connect to a TPM simulator. Optional. | swtpm:port=2321        |

See the project in [examples\cpp\dds\SecureHelloWorldWithTPMExample](examples\cpp\dds\SecureHelloWorldWithTPMExample) for a working configuration example.

Note that in order for a participant to generate attestation evidence, all properties except `privacy_ca` and `tcti_options` must be set.
The quoting key can be specified either as a TPM handle with the `handle:` prefix, or using the serialized object file generated by TPM2 Tools (e.g., `object:quotingkey.tr`).
The CA and quoting key certificates must be PEM-encoded files.
The PCR banks are specified as a comma-separated list using any of: sha1, sha256, sha384, sha512, sm3_256.
The PCR registers can be specified as a comma-separated list of integer ranges.
However, make sure to only configure PCR banks and registers that are *actually supported* by your platform TPM, because otherwise the DDS handshake will fail (there is no silent ignore of unsupported PCR banks and registers like in the TPM2 Tools).

If you do not set any of the mandatory properties listed above, the participant will not generate quotes for the local platform.
However, the participant can still receive and verify attestation evidence from remote peers.
This allows you to set up *uni-directional* attestation scenarios as well.
By default, the `dds.sec.auth.builtin.PKI-DH.identity_ca` property will be used to verify received attestation key certificates.
If you operate a dedicated CA for attestation keys, you can override this setting using the optional `privacy_ca` property listed above.

Finally, note that the modified DDS software stack contained in this repository is fully backwards-compatible with the original FastDDS implementation.
This means that any DDS participant configured to conduct remote attestations can still communicate safely with remote participants using the original (unmodified) PKI-DH plugin.
However, in this case no quotes are exchanged during the DDS handshake, since the remote participant with the unmodified software stack could not verify them anyway.

*eprosima Fast DDS* (formerly Fast RTPS) is a C++ implementation of the DDS (Data Distribution Service) standard of the OMG (Object Management Group). eProsima Fast DDS implements the RTPS (Real Time Publish Subscribe) protocol, which provides publisher-subscriber communications over unreliable transports such as UDP,
as defined and maintained by the Object Management Group (OMG) consortium. RTPS is also the wire interoperability protocol defined for the Data Distribution
Service (DDS) standard. *eProsima Fast DDS* expose an API to access directly the RTPS protocol, giving the user full access to the protocol internals.

Some of the main features of this library are:

* Configurable best-effort and reliable publish-subscribe communication policies for real-time
applications.
* Plug and play connectivity so that any new applications are automatically discovered by any other
members of the network.
* Modularity and scalability to allow continuous growth with complex and simple devices in the
network.
* Configurable network behavior and interchangeable transport layer: Choose the best protocol and
system input/output channel combination for each deployment.
* Two API Layers: a high-level Publisher-Subscriber one focused on usability (DDS) and a lower-level Writer-Reader one that provides finer access to the inner workings of the RTPS protocol.

*eProsima Fast DDS* has been adopted by multiple organizations in many sectors including these important cases:

* Robotics: ROS (Robotic Operating System) as their default middleware for every ROS 2 long term (LTS) releases and most of the non-LTS releases.
* EU R&D: FIWARE Incubated GE.

This project is part of [FIWARE](https://www.fiware.org/). For more information check the FIWARE Catalogue entry for
[Robotics](https://github.com/Fiware/catalogue/tree/master/robotics).

## Quick Demo

eProsima provides the eProsima Fast DDS Suite Docker image for those who want a quick demonstration of Fast-DDS running on an Ubuntu platform. It can be downloaded from [eProsima's downloads page](https://eprosima.com/index.php/downloads-all).

This Docker image was built for Ubuntu 20.04 (Focal Fossa).

To run this container you need **Docker installed**. From a terminal run the following command

    $ sudo apt-get install docker.io

Load the docker image:

    $ docker load -i ubuntu-fastdds-suite:<FastDDS-Version>.tar
    $ docker tag ubuntu-fastdds-suite:<FastDDS-Version> ubuntu-fastdds-suite:latest

Run the eProsima Fast DDS Suite Docker container:

    $ xhost local:root
    $ docker run -it --privileged -e DISPLAY=$DISPLAY -v /tmp/.X11-unix:/tmp/.X11-unix \
    ubuntu-fastdds-suite:<FastDDS-Version>

This Docker Image comes bundled with the following:

### Shapes Demo

eProsima Shapes Demo is an application in which Publishers and Subscribers are shapes of different
colors and sizes moving on a board. Each shape refers to its own topic: Square, Triangle or Circle.
A single instance of the eProsima Shapes Demo can publish on or subscribe to several topics at a
time.

You can read more about this application on the
[Shapes Demo documentation page](https://eprosima-shapes-demo.readthedocs.io/).

To run this application once inside the Docker container run:

    $ ShapesDemo

eProsima Shapes Demo usage information can be found on the
[Shapes Demo First Steps page](https://eprosima-shapes-demo.readthedocs.io/en/latest/first_steps/first_steps.html).

### Fast DDS Monitor

eProsima Fast DDS Monitor is a graphical desktop application aimed at monitoring DDS environments
deployed using the *eProsima Fast DDS* library. Thus, the user can monitor in real time the status
of publication/subscription communications between DDS entities. They can also choose from a wide
variety of communication parameters to be measured (latency, throughput,packet loss, etc.), as well
as record and compute in real time statistical measurements on these parameters (mean, variance,
standard deviation, etc.).

You can read more about this application on the
[Fast DDS Monitor documentation page](https://fast-dds-monitor.readthedocs.io/).

To run this application once inside the Docker container run:

    $ fastdds_monitor

eProsima Fast DDS Monitor usage information can be found on the
[Fast DDS Monitor User Manual](
https://fast-dds-monitor.readthedocs.io/en/latest/rst/user_manual/initialize_monitoring.html).


### Fast DDS libraries and Examples

Included in this Docker container is a set of binary examples that showcase several functionalities of the
Fast DDS libraries. These examples' path can be accessed from a terminal by typing

    $ goToExamples

From this folder you can access all examples, both for DDS and RTPS. We detail the steps to launch two such
examples below.

To launch the Hello World example (a minimal example that will perform a Publisher/Subscriber match and start
sending samples) you could run:

    $ goToExamples
    $ cd dds/HelloWorldExample/bin
    $ tmux new-session "./HelloWorldExample publisher 0 1000" \; \
    split-window "./HelloWorldExample subscriber" \; \
    select-layout even-vertical

This example is not constrained to the current instance. It's possible to run several instances of this
container to check the communication between them by running the following from each container.

    $ goToExamples
    $ cd dds/HelloWorldExample/bin
    $ ./HelloWorldExample publisher

or

    $ goToExamples
    $ cd dds/HelloWorldExample/bin
    $ ./HelloWorldExample subscriber

Another example you could launch is the Benchmark example. This example creates either a Publisher or a Subscriber and
on a successful match starts sending samples. After a few seconds the process that launched the Publisher will show
a report with the number of samples transmitted.

On the subscriber side, run:

    $ goToExamples
    $ cd dds/Benchmark/bin
    $ ./Benchmark subscriber udp

On the publisher side, run:

    $ goToExamples
    $ cd dds/Benchmark/bin
    $ ./Benchmark publisher udp
