# TPM-enabled Fast DDS
This repository contains a fork of the eProsima FastDDS implementation, extended by TPM-based remote attestation.
Try it out using the included Dockerfile.
```
git clone https://gitlab.cc-asp.fraunhofer.de/ros2-security/fast-dds-tpm && cd fast-dds-tpm
docker build -t fast-dds-tpm .
docker run --rm -it fast-dds-tpm
> cd install/examples/cpp/dds/SecureHelloWorldWithTPMExample/bin/
> ./generate_quoting_key.sh /CN=myQuotingKey/OU=myCompany
> ./DDSSecureHelloWorldWithTPMExample publisher &
> ./DDSSecureHelloWorldWithTPMExample subscriber
```

## Prerequisites
This fork of FastDDS extends the DDS PKI-DH authentication and access control plugins with TPM-based remote attestation capabilities.
The only additional prerequisite is the [TPM 2.0 TSS](https://github.com/tpm2-software/tpm2-tss), which can be installed from the package manager with most Linux distributions.
```
apt-get install -y tpm2-tools tpm2-openssl man-db libtss2-dev
```

## Prepare the TPM
To enable remote attestation in DDS, you first need to prepare an attestation key inside the TPM.
You can use the powerful [TPM2 Tools](https://tpm2-tools.readthedocs.io) for this.
```
# Create a new endorsement key with handle 0x81010001.
# You can skip this step if your TPM already has an EK provisioned (like the simulator in the Dockerfile).
tpm2_createek -c 0x81010001 -G rsa -g sha256

# Create a new attestation key under the EK and make it persistent
tpm2_createak -C 0x81010001 -G rsa -g sha256 -c quotingkey.ctx
tpm2_evictcontrol -c quotingkey.ctx -o quotingkey.tr
```

You also need to generate a certificate for the created attestation key that is signed by your CA.
To try out remote attestation in DDS, it is sufficient to just use the TPM provider of OpenSSL for this.
```
openssl req -provider tpm2 -provider default -propquery '?provider=tpm2' -new -subj "/CN=myQuotingKey/OU=myCompany" -key object:quotingkey.tr -out quotingkey.csr
openssl x509 -req -CA maincacert.pem -CAkey maincakey.pem -days 730 -in quotingkey.csr -out quotingcert.pem
```
ATTENTION:
Note that generating a self-signed CSR for the attestation key like that does not allow the CA to verify that the attestation key is in fact protected by a genuine TPM.
Hence, in production scenarios you should instead establish a proper provisioning process for attestation keys and certificates, following the TCG guidelines.
Refer to [TPM 2.0 Keys for Device Identity and Attestation](https://trustedcomputinggroup.org/wp-content/uploads/TCG_IWG_DevID_v1r2_02dec2020.pdf) for further details.

## Configure Remote Attestations
To configure a DDS participant for remote attestation, all you need to do is to set the following QoS properties in the `dds.sec.auth.builtin.PKI-DH.tpm2` namespace.

| Property      | Description                                                          | Example                |
| ------------- | -------------------------------------------------------------------- | ---------------------- |
| quoting_key   | Attestation key to use for generating quotes.                        | handle:0x81000000      |
| quoting_cert  | CA-signed certificate authenticating the attestation key.            | file[]()://quotingcert.pem |
| privacy_ca    | CA certificate to authenticate remote attestation keys. Optional.    | file[]()://maincacert.pem  |
| pcr_banks     | PCR banks to include in the generated quotes.                        | sha1,sha256            |
| pcr_selection | PCR registers to include in the generated quotes.                    | 0-7,10                 |
| tcti_options  | TCTI parameter string, e.g. to connect to a TPM simulator. Optional. | swtpm:port=2321        |

See the project in [SecureHelloWorldWithTPMExample](examples/cpp/dds/SecureHelloWorldWithTPMExample) for a working configuration example.

Note that in order for a participant to generate attestation evidence, all properties except `privacy_ca` and `tcti_options` must be set.
The quoting key can be specified either as a TPM handle with the `handle:` prefix, or using the serialized object file generated by TPM2 Tools (e.g., `object:quotingkey.tr`).
The CA and quoting key certificates must be PEM-encoded files.
The PCR banks are specified as a comma-separated list using any of: sha1, sha256, sha384, sha512, sm3_256.
The PCR registers can be specified as a comma-separated list of integer ranges.
However, make sure to only configure PCR banks and registers that are *actually supported* by your platform TPM, because otherwise the DDS handshake will fail (there is no silent ignore of unsupported PCR banks and registers like in the TPM2 Tools).

If you do not set any of the mandatory properties listed above, the participant will not generate quotes for the local platform.
However, the participant can still receive and verify attestation evidence from remote peers.
This allows you to set up *uni-directional* attestation scenarios as well.
By default, the `dds.sec.auth.builtin.PKI-DH.identity_ca` property will be used to verify received attestation key certificates.
If you operate a dedicated CA for attestation keys, you can override this setting using the optional `privacy_ca` property listed above.

Finally, note that the modified DDS software stack contained in this repository is fully backwards-compatible with the original FastDDS implementation.
This means that any DDS participant configured to conduct remote attestations can still communicate safely with remote participants using the original (unmodified) PKI-DH plugin.
However, in this case no quotes are exchanged during the DDS handshake, since the remote participant with the unmodified software stack could not verify them anyway.
